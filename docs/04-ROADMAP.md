# 04 — План работ

Порядок не по важности замысла, а по отношению «эффект ÷ стоимость».
Оценки в вечерах, не в днях.

Правило: **не начинать уровень, пока не закрыт предыдущий.** Причина —
каждый следующий уровень опирается на предыдущий, и без основания
превращается в новый мёртвый код, которого в проекте уже около 900 строк.

---

## Уровень 0 — без этого игры нет

Две поломки. Обе структурные, обе дешёвые, обе меняют игру целиком.

### 0.1 Цепочка приказа · 1–2 вечера

Сейчас приказ исполняется в обход характера. Надо, чтобы он входил
в голосование и мог проиграть.

**`Warrior.cs`** — приказ записывается, а не исполняется:

```csharp
[System.Serializable]
public struct PendingCommand
{
    public string Type;        // "Attack", "Move", "Defend", "Hold"
    public Vector3 Point;
    public GameObject Target;
    public bool IsSet;
}

public PendingCommand Command;

public void IssueCommand(string type, Vector3 point, GameObject target = null)
    => Command = new PendingCommand
       { Type = type, Point = point, Target = target, IsSet = true };

public void ClearCommand() => Command = default;
```

**`SelectionManager.HandleCommandInput`** — вместо прямого управления:

```csharp
// было:  mover.CommandAttack(enemyUnit.gameObject);
// стало:
unit.GetComponent<Warrior>()?.IssueCommand("Attack", hit.point, enemyUnit.gameObject);

// было:  mover.CommandMove(hit.point);
// стало:
unit.GetComponent<Warrior>()?.IssueCommand("Move", hit.point);
```

**`AOSWarriorWrapper.Decide`** — приказ становится фактом контекста:

```csharp
var cmd = _warrior.Command;
var context = CombatDecisionContext.Create(_warrior, cmd.IsSet ? cmd.Type : "");
```

**`AOSWarriorWrapper.Execute`** — ветка подчинения:

```csharp
case ActionType.ObeyCommand: ExecuteCommand(); break;

private void ExecuteCommand()
{
    var cmd = _warrior.Command;
    if (!cmd.IsSet) return;
    var mover = GetComponent<UnitMover>();
    if (cmd.Target != null) mover?.CommandAttack(cmd.Target);
    else mover?.CommandMove(cmd.Point);
    _warrior.ClearCommand();
}
```

**И главное — отказ:**

```csharp
if (_warrior.Command.IsSet && action != ActionType.ObeyCommand)
    AOSEventHub.ReportRefusal(_warrior, action);
```

После этого `LoyaltyModule` оживает, а `GreedObeyUnpaidPenalty = -40`
из `AOSConfig` начинает работать: три невыплаты — и приказ проигрывает золоту.

> **Проверка:** создать двух воинов — верного и жадного с тремя невыплатами.
> Отдать обоим один приказ рядом с сундуком. Верный идёт. Жадный — нет.
> Если это работает, Sinbinder существует.

### 0.2 Семь спектров вместо одного числа · 2–3 вечера

Сейчас все воины — один коктейль. Пока это так, любая работа над
разнообразием бессмысленна.

**`SoulData.cs`**:

```csharp
[SerializeField] private float[] _spectra = new float[7];   // индекс = (int)SinType

public float GetSpectrum(SinType sin) => _spectra[(int)sin];

public void ChangeSpectrum(SinType sin, float delta)
    => _spectra[(int)sin] = Mathf.Clamp(_spectra[(int)sin] + delta, -100f, 100f);

// Обратная совместимость: доминирующий грех — максимум по модулю
public SinType Sin
{
    get
    {
        int best = 0;
        for (int i = 1; i < 7; i++)
            if (Mathf.Abs(_spectra[i]) > Mathf.Abs(_spectra[best])) best = i;
        return (SinType)best;
    }
}

public float SinIntensity => GetSpectrum(Sin);
```

**`Soul.cs`** (адаптер) — везёт весь набор:

```csharp
public float[] Spectra;
public float Get(SinType s) => Spectra[(int)s];
```

**Каждый модуль** читает свою шкалу:

```csharp
// GreedModule
float sin = soul.Get(SinType.Greed);     // было soul.SinIntensity
// WrathModule
float sin = soul.Get(SinType.Wrath);
// SlothModule
float sin = soul.Get(SinType.Sloth);
```

Добродетели при этом исчезают как отдельная сущность: щедрость —
это Жадность со знаком минус. Семь шкал вместо четырнадцати понятий.
`VirtueModule` становится не нужен как отдельный модуль — его логика
переезжает в отрицательную половину каждой шкалы.

> **Проверка:** три воина с одинаковой суммарной «силой», но разными
> пиками. В одной и той же ситуации они должны выбрать разное.

## Уровень 1 — без этого игру не понять

Провал №1 из `01-VISION.md`: игрок не понимает, что произошло, и решает,
что ИИ сломан. Это самая частая причина смерти игр такого типа.

### 1.1 Момент отказа как событие · 2 вечера

Отказ — это продукт. Сейчас он неотличим от обычного хода.

Когда `ObeyCommand` проигрывает: короткое замедление, значок победившего
действия крупно, звук `VoiceGenerator` в тембре доминирующего греха,
одна реплика над головой.

Реплики берутся из `DialogueSituation` по ключу «грех + мораль» — система
для этого уже есть и работает.

### 1.2 Журнал боя человеческим языком · 2–3 вечера

`BattleRecord` заполняется, но нигде не показывается. Нужен экран
после боя, где каждое решение — предложение, а не строка чисел.

```
Марга Копатель не пошёл на мост.
Ему не платили третью вылазку подряд, а в развалинах блестело золото.
Приказ он слышал. Просто золото было громче.
```

Правило без исключений: **ни одной цифры**. Это Принцип из `02-AOS.md`.

Технически: `BehaviourResolver` возвращает не только победителя, но и
причину — какой модуль дал решающий перевес и какой факт контекста
его вызвал. Одна структура `DecisionTrace`, заполняется там же, где
сейчас стоит `Debug.Log`.

### 1.3 Подсказка при наведении · 1 вечер

Ступень 2 лестницы прозрачности. Наводишь на воина — одна фраза:
«Золото ближе, чем приказ». Читает ту же `DecisionTrace`.

### 1.4 Разбор перед вылазкой · 2 вечера

Перед отправкой отряда — не проценты, а характеристики:
«Рык, вероятно, не отступит». «Марге не платили дважды».
Это фаза искушения: игрок видит риск и решает, чем его перебить.

## Уровень 2 — без этого нет глубины

### 2.1 Подключить перки · 1 вечер

Сто перков написаны и не влияют ни на что. Нужна **одна строка**
в `BehaviourResolver.Decide`, перед сортировкой:

```csharp
PerkResolver.ApplyPerks(scores, warrior, context, _perkDatabase);
```

Плюс поле `_perkDatabase` через `Resources.Load<PerkDatabase>` — как
это уже делают модули с `AOSConfig`.

Лучшее соотношение эффекта к стоимости во всём проекте: один вечер
оживляет 77 КБ готового контента.

### 2.2 Набор действий из умений · 2 вечера

Вместо жёстких шести — собирать кандидатов из того, что воин умеет:
базовые действия + навыки класса + навыки доминирующего греха +
разблокированное перками. Так 56 написанных навыков войдут в игру.

### 2.3 Один кризис до конца · 3 вечера

Не все тринадцать. Один: **невыплата → требование → уход**.

Канон — `Core/Crisis/*` (данные + варианты выбора), а не
`AOS Engine/CrisisType.cs` (хардкод-`switch`). Причина: принцип
«данные управляют поведением». Вторую реализацию удалить.

Игрок получает выбор: заплатить, отказать, пообещать. У каждого —
последствия в памяти и отношениях. Это первое место, где характер
воина обходится игроку в ресурс.

### 2.4 Цена потери · 2 вечера

Пока смерть воина ничего не стоит, личность не важна. Механизм уже
спроектирован — качество души по времени с момента смерти
(`SoulQuality`: Шок → Принятие → Угасание → Раствор). Надо
подключить: не успел собрать — душа ушла навсегда, вместе со всей
её памятью, титулами и перками.

## Уровень 3 — масштаб

### 3.1 Автономные миссии · 3–4 вечера
`MissionResolver`, `Quest`, `FalseGodQuest` написаны и не вызываются.
Отправил отряд — вернулся с исходом, определённым характером командира.
Это второй игровой режим почти без нового кода.

### 3.2 Слухи · 2 вечера
`RumourManager` мёртв. Оживить — и мир начнёт реагировать на репутацию:
слух о предательстве расходится по отряду и меняет верность у тех,
кто ничего не видел лично.

### 3.3 Модули из реестра · 1 вечер
Сейчас восемь модулей зашиты в конструктор `BehaviourResolver`.
Вынести в `ScriptableObject`-список. Добавление греха станет
добавлением данных. Заодно подключить забытый `PatienceModule`.

### 3.4 Производительность · 2 вечера
Около 13 аллокаций на решение. Массив вместо словаря, буфер вместо
`new Soul`, ручной максимум вместо LINQ. Делать, когда воинов станет
больше десяти, не раньше.
