# Sinbinder — развитие существующего редактора карт до уровня World Editor

**Решение автора:** редактор должен работать по принципам Warcraft III World Editor, но оставаться редактором Sinbinder, а не копией Warcraft III. Работать поверх существующих `MapEditor.cs`, `MapData.cs`, `MapLoader.cs`, `MapLogicRunner.cs`, а не создавать независимый второй редактор. **Статус:** спецификация + первый реальный ограниченный патч, без Unity PlayMode; не полный готовый World Editor.

**Порядок исполнения:** текстовый аудит по авторскому решению 18.11 продолжает действовать до пяти независимых проходов и отдельного разрешения. Эту спецификацию можно использовать как следующий этап, а сделанные ниже изолированные изменения не объявляют UX-спринт открытым.

## 1. Проверенное существующее состояние

- Единственный встроенный редактор `Assets/Scripts/Gameplay/MapEditor.cs`, настоящая сцена `Assets/Scenes/Tug/MapEditor.unity`, `MapData` и `MapLoader` обслуживают те же JSON-карты режима «Перетягивание каната».
- Существуют палитра моделей, склепы игроков (2–8), деревни/лес/поле, тропы охотников, события, области, размещение/выделение/удаление, поворот Q/E, привязка к сетке, поиск, свойства в инспекторе, копирование, отмена/повтор, проверка карты, атомарное сохранение и резервная копия .bak.
- Имеется безопасная ECA-система: старт карты/вход в область/взаимодействие F, одна проверка флага, показ сообщения или установка флага. События локальные, не запускают C#, JASS, Lua, Reflection и не работают с файловой системой.
- Первым патчем расширено: `FlagIsFalse`, `ClearFlag`, кнопка «Добавить событие взаимодействия (F)» в инспекторе выбранного объекта. Старые JSON поля и поведение остаются совместимыми. Тестовый стенд `Tools/map-editor` компилирует реальные C#-файлы с Unity-заглушками, но **это не Unity**.

## 3. Предлагаемый внешний вид

Привычная раскладка Warcraft III World Editor, но в оформлении Sinbinder:

```text
┌ Файл   Правка   Вид   Карта   Сценарий   Проверить   Сохранить ─────┐
│ [Объекты] [Рельеф] [Декорации] [Геймплей] [Триггеры]  [▶ Тест] │
├──────────────────┬───────────────────────────┬────────────────────┤
│ ПАЛИТРА          │                           │ ИНСПЕКТОР          │
│ поиск: [______]  │    3D / вид сверху        │ Объект: «Ворота»    │
│ > Окружение      │                           │ ID: stable-uuid     │
│ > Постройки      │     рельеф / карта        │ Позиция: X,Y,Z     │
│ > Стражи         │     ◯ области             │ Поворот: ...       │
│ > Триггеры       │     ▣ выбранный объект    │ Тип: интерактивный │
│ > Избранное      │                           │ [F: действие]      │
│                  │                           │ [Триггер: открыть] │
├──────────────────┴───────────────────────────┴────────────────────┤
│ Проблемы: 0   | Изменено*  | Ctrl+Z/Y  | Карта: MyMap.json      │
└───────────────────────────────────────────────────────────────────┘
```

Дополнительно: вкладка «Сценарий» как редактор ориентированного графа:
```text
[Событие: игрок вошёл в Зону_1]
                ↓
 [Условие: ключ_найден == true]
        ↙                    ↘
     [ДА]                   [НЕТ]
       ↓                      ↓
 [Открыть ворота]     [Показать: «Заперто»]
```
Этот граф — **концепция**, не уже реализованный редактор узлов. Начать с проверяемой линейной ECA; визуальные соединители только после устойчивой модели данных и диагностики.

## 4. Можно ли программировать предметы?

**Да.** Предмет имеет стабильный `Thing.Id`, а `OnInteractObject` использует его через общую систему взаимодействия `F`. Пример без компиляции кода:

- Поставить «Камень» (или другой доступный prefab), выделить его, нажать «Добавить событие взаимодействия (F)».
- В открытом правиле установить событие `OnInteractObject`, условие `FlagIsFalse`, флаг `seal_broken`, действие `ShowMessage` с текстом «Печать ещё цела».
- Другое событие в той же области устанавливает `seal_broken` через `SetFlag`.
- После этого новое правило с `FlagIsTrue` показывает «Печать снята». `ClearFlag` позволяет заново сбросить состояние.

Граница текущего выполнения: это **текст и логические флаги**, пока нет операции по реальному открытию модели ворот, изменения коллайдера, лута, запуска анимации или воздействия на AOS. Такие действия можно безопасно добавлять по одному через whitelist с валидаторами владельца компонента.

Для общедоступных карт нельзя запускать текст сценария как C#/Lua/JASS из JSON. Любой скрипт должен проходить sandbox/лимиты времени, памяти и API; на первом этапе достаточно data-only ECA.

## 5. Архитектура следующего цикла

1. **MapData v3**: дополнительные необязательные списки TerrainStroke, Layer, ObjectComponent и наборы типизированных переменных, с EnsureLists для устаревших JSON.
2. **MapLoader**: детерминированное применение данных мира, привязка объектов к высоте, NavMesh после террейна, спавн с проверкой пересечений. Не изменять стандартные сцены демо.
3. **MapEditor**: каталог по категориям, 3D-превью, gizmos, brush, инспектор и слой; editor commands через централизованный транзакционный Undo вместо множества разнородных правок.
4. **MapLogicRunner**: explicit event registry, typed whitelist, ограничение количества событий/действий за кадр, сериализация локального состояния при необходимости, tracing для отладки. Стартовый лимит 128 triggers уже есть.
5. **Интеграция AOS**: только через публичные методы игровых компонентов, без изменения расчётов АОS непосредственно картой.
6. **Test map pipeline**: unit source tests → Unity EditMode compile → PlayMode editor→save→load→F→event→effect, карта на двоих и карта на четверых, проверка загрузки старых файлов.

## 6. Приоритет реальных итераций

**Итерация 1 (в текущем коммите):** расширение флагов, быстрое создание событий предмета, tests и existing .json compatibility. Статус нужен по фактическому CI, Unity NOT VERIFIED.

**Итерация 2:** UI каталог с фильтрами и подсказками, preview «под курсором», выбор сразу нескольких объектов, свойства/слои, защита от случайной потери данных.

**Итерация 3:** настоящий изменяемый рельеф с heightmap/strokes и roundtrip JSON, потом NavMesh/высоты/боевые тесты. Не создавать фальшивый brush, который меняет картинку редактора, но не игровую карту.

**Итерация 4:** расширяемые triggers для дверей/сундуков/наёмников/склепов/кастомных задач, сначала по одному проверенному действию.

**Итерация 5:** editor playtest, автодиагностика, шаблоны, экспорт карт.

## 7. Риски, которые нельзя игнорировать

- Уже написанные JSON-карты и игры должны открываться. Новые поля только необязательные, новое поведение по умолчанию безопасно.
- Runtime MapEditor использует IMGUI; при 3D-сцене и длинных списках нужен eventual UIToolkit, но без «переписать всё и потерять рабочие карты».
- Прямые изменения `MapLoader` влияют на боевой runtime и multiplayer; внедрять отдельно с PlayMode приёмкой.
- Установка произвольного кода, сетевых или файловых действий из пользовательских карт недопустима.
- Ресурсы и prefab должны браться из белого списка; нельзя передавать произвольный путь, файл или type string.
- Параллельные сессии не должны мержить несовместимые ветки редактора без проверки schema и тестов.
- Редактор должен оставаться удобным даже автору, который запускает Unity около одного раза в неделю: сохранять диагностику, откаты и воспроизводимые тесты.

**Текущий вывод:** полноценный аналог Warcraft III World Editor — крупный отдельный этап; в этом обновлении внедряется основа программирования через существующие карты и предметы. Нельзя считать рельеф, сценарный граф или логику настоящих ворот реализованными, пока их нет в коде и Unity-тестах.
