# Sinbinder — подробный рабочий план сессии QA И ИНТЕГРАЦИЯ
Владелец: «QA и интеграция Sinbinder», ежечасно около :53. Обязательны 00-TEAM-CHARTER.md, issue #3, план Assets/Scripts/docs/57-MULTIPLAYER-PRIORITIES-HANDOFF.md.
Это независимый контроль качества пяти направлений, а не разрешение переписывать систему любого из них.

## 1. Миссия
Доказать, что изменения мультиплеера, визуала, UX и логики совместимы в одном реальном Unity 6000.3.22f1 проекте и не ломают одиночное демо. QA обязан отделять «файл существует», «.NET mock test passed», «Unity Editor compiled», «Unity Player runs» и «2 физических ПК прошли матч». Миссия — закрывать критические риски раньше расширения систем.

QA имеет право отмечать релизную/merge блокировку S0/S1 в issue #3 и PR, но не обладает автоматической технической блокировкой ветки. Не заявлять, что он остановил пуш другой сессии; при необходимости передать пользователю.

## 2. Ежечасный тестовый цикл
1. Прочесть HEAD, последние коммиты за 1–2 часа (включая сессии UX/AOS), активные workflows и последние сообщения issue #3. Не предполагать, что одна сессия закончила свой запуск до следующей.
2. Проверить, нет ли красного CI на HEAD. Если падает общий tutorial-smoke, сначала разобрать точный шаг и toolchain, а не приписывать ошибку мультиплееру.
3. Выбрать один тестируемый cross-system риск — предпочтительно первый P0/P1 блокер. Подготовить шаги воспроизведения, ожидаемый результат и доказательство.
4. Не менять файлы другого владельца без дополнительной проверки SHA/координации. При необходимости сделать отдельный тест/скрипт или передать находку.
5. После минимального патча/теста — сверить CI именно на новом SHA; при падении расследовать/откатить собственное изменение. При отсутствии патча допустим качественный аудит без фиктивного коммита.
6. Сохранить матрицу уровней L0–L7 из 00-TEAM-CHARTER и сообщить пользователю/соседям фактическую границу проверок.

## 3. Главный P0-гейт: настоящая Unity, не заглушки
### Q0.1 — Импорт/компиляция (P0, M)
- Проверить Unity 6000.3.22f1, Packages/manifest.json, Graphics/URP, scene list, API изменения Editor vs Player, assembly definitions, scripting define symbols, целостность .meta GUID.
- Поднять чистую копию feature/server-prototype (ни одной установки в main). Сборка «Собрать игру.cmd» → Tools/play/build-game.ps1 должна работать без невидимых ручных шагов. На Windows учитывать полные пути, Unicode, пробелы, требования лицензии/модулей Unity.
- Проверить Assets/Scenes/Tug/Multiplayer_Test.unity и Field: нет Missing Script, нерешённых compile errors, отсутствующих материалов/шейдеров.
- Собрать реальные Windows Player и headless host, записать Unity Editor версия, SHA, целевые платформы, параметры BuildPipeline, время сборки и лог ошибок.
Приёмка Q0.1: реальная L3 compile + build output с файлами и логами. Если Unity недоступна: только преполётная статическая проверка и статус BLOCKED, не PASS.

### Q0.2 — Реальная LAN-вертикаль (P0, M)
- Открыть один Unity world host + два независимо работающих клиента: Test-World-Auto.cmd / Test-World-Auto.ps1, порт выбран явно. Перед запуском убедиться, что exe собран из того же HEAD, не слепо доверять только timestamp.
- Приёмка по логу: сервер слушает и зарегистрировал двух Lord, у каждого клиента свой playerId, same match, private own Lord ActorId, корректный gameMatch, отправка/принятие/доставка Move, фактическое NavMesh перемещение двух Lord, HP valid, world snapshots и нормальное завершение.
- Зафиксировать WorldHost.log, Client1.log, Client2.log, SHA, exit codes, время и оборудование. Если один PASS, другой FAIL — весь тест FAIL.
- Проверить, что карта действительно Multiplayer_Test, есть два crypts, нужный actor exists/привязан к правильной стороне, не конфликтует RivalLord AI.
- Дополнительный ручной Test-World-LAN.cmd (F8) и прежний Test-LAN.cmd (капсулы) — два разных теста, нельзя путать результаты.
Приёмка Q0.2: L5, без NullReference, MissingReference, бесконечных ожиданий и ошибки видимости.

### Q0.3 — Регрессия одиночного режима (P0, M)
- Пройти ключевые моменты уже играбельного соло: запуск/сцена Field, движение/камера, Tab, V, выбор воинов ЛКМ/приказ ПКМ, боевая атака/блок, AOS согласие и отказ, смерть, сбор души, алтарь, сохранность руководящих UI компонентов.
- Выйти из LAN теста, убедиться, что Scene, Input, SelectionManager, Camera, TimeScale и AudioListener возвращаются корректно.
- Проверить, не отключился ли RivalLord AI в соло после сетевого теста; сеть не должна оставить server-only listeners/дубликаты.
Приёмка Q0.3: Play Mode L4 + лог/видео/проверочный список, не только просмотр методов.

## 4. Сквозная функциональная матрица (P1–P3)
### Q1. Game state / identity
- ServerId стабилен между frames, корректен при respawn/rebind, уникален, клиент не назначает собственный ID.
- Two Lords имеют разный owner, neutral может реагировать на обоих, чужой приказ вражескому Lord отклоняется.
- Spawn/despawn/death/late join, partial snapshot/invalid tick/NaN, скрытый актёр исчезает после revoke visibility, нет stale ghost.
- Идентичность после disconnect/reconnect не присваивает другой стороне чужого Lord. Проверять старые пакеты, повтор CommandId, late results.

### Q2. AOS + причинность
- Отправка приказа → авторизация → AOS verdict → исполнение: подтверждения разные, причина отказа настоящая.
- Сценарии «воин боится», «другой Lord», «сильный аргумент против большинства», «спасение», «предательство», «память после изменения контекста».
- Без direct override AOS ради урока; экзамен обучения требует самостоятельного действия.
- Race conditions: цель умирает между командой и execute tick; воин меняет allegiance; AFK/timeout.

### Q3. Combat, soul, resources
- Реальное попадание/блок/промах, HP и UI/VFX/звук в одном порядке, нет повторного урона от duplicate event.
- Две стороны одновременно убивают/подбирают одну душу, кладут тело в сокет, платят ресурсы. Только сервер определяет итог, без double-spend.
- Смерть Lord, трон, условия победы, остановка партии, ввод после конца — обрабатываются однозначно.
- Replay/resume не создаёт второй лут, вторую душу, второе тело или дублированного Warrior.

### Q4. Visual + camera + input
- В tactical и FPS совпадает выбор и положение сущностей; V не меняет камеру, Tab не меняет роль неправильно.
- URP/material/FBX/shadows, GPU; отсутствие pink shader, скрытых из-за интерфейса задач, clips и missing assets.
- Игра читабельна на 1280×720 и 1920×1080; подсказки, прицел, карточка AOS не закрывают бой.
- Нейтральный/свой/вражеский статус не раскрывает hidden FOW актёра и не зависит только от цвета.

### Q5. Tutorial + recovery
- Новичок может ошибиться в любом уроке и исправить ситуацию. Никакого guaranteed AOS obedience и невыполнимых целей.
- Реальное спасение против реальной атаки, страх при наличии угрозы, печатки/порог/радиус, независимый финальный экзамен.
- Нет «засчитали, потому что выполнили Debug Warp», старого контекста между учебными задачами или зависания после смерти учителя.
- Пропуск/перезапуск/сейв после разрыва кат-сцены проверяется настоящим сценарием.

## 5. Тесты сети и безопасных комнат (P3–P4)
Q5.1: LAN TCP недоверенный. Fuzz size, bad JSON, unknown type, seq replay, NaN/Infinity, oversize packet, буфер, heartbeat timeout, disconnect near tick.
Q5.2: Тест комнаты: wrong password, 5 guesses/lockout, попытка от другого connectionId, full room, last owner leave, rate limit spam, недопустимый host/port.
Q5.3: Passwords/TLS. Не подключать приватные комнаты к plaintext TCP без защищённого транспорта. Проверить невывод секретов в logs и HTTP/API.
Q5.4: Ping fairness Off/Conservative/Balanced, серверный RTT на двух клиентах и отклонение поддельного client RTT. Реальная сеть 20/80/150/250 ms; проверить exploit задержки pingReply.
Q5.5: Windows/Linux Dedicated Server, VPS: тест firewall/healthcheck/отказа сервиса, client version mismatch, off-by-one version. Никакого публичного развёртывания без разрешения.

## 6. Автотесты и CI как инфраструктура
- Проверить каждый GitHub workflow на текущем SHA; результаты разных jobs могут противоречить. Не писать «все зелёные», если хотя бы один критичный workflow красен.
- Tools/server/UnityLanHarness: компилируются настоящие multiplayer source files с Unity API shim, но не вся игра. Дополнять проверяемые ветки, а не заменять реальные Play Mode.
- Tools/server/check_map_assets.py: GUID, scene serialization, version constraints; если внесена сцена/ассет — .meta и ссылку проверить обязательно.
- Tutorial tests: новые Roslyn SyntaxChecks могут зависеть от SDK версии, например историческая CS1705 (net8 + Roslyn SDK10). При повторе диагностировать toolchain и передать UX/логику, не менять мирные механики ради green badge.
- Настоящий Unity CI возможен только при наличии лицензии/runner/секретов; не выдавать отсутствие runner за «успешный Unity».
- Увеличивать assertions только с реальной проверкой: tests должны падать при возвращении регрессии. Следить за хрупкими тестами, stale snapshots и портовыми конфликтами при параллельных workflow.

## 7. Стресс-тесты и долгий матч (P4–P5)
- 2 разных машины, затем закрытая VPN/VPS. 30–60 минут игры с 20/50/100+ Warrior по готовности систем; отчёт FPS, CPU/RAM/GC, RTT/jitter/packet loss, длина очередей, timeout, время рассинхронизации.
- При переходах: warm start, disconnect одного клиента на 5/20 сек, resuming, host shutdown/crash, повторный матч, версия клиента не совпадает.
- Проверять порядок snapshot vs game events, отсутствие out-of-order UI анимаций, отсутствие leaks in worldActor.
- Диагностический запуск 2 капсул не равен длительному матчу с AOS/алтарём.

## 8. Журнал регрессий и приоритеты
Требовать для каждого бага: явный SHA, точный путь, воспроизводимые шаги, лог/скриншот при наличии, ожидаемый и фактический результат, тяжесть S0/S1/S2/S3, level L0–L7, владелец исправления. Если баг не воспроизведён — гипотеза, не подтверждённый S1.
QA сообщает коллегам: Мультиплееру — state/protocol/ownership bugs; Визуалу — missing shader/clipping/scene; UX — тупики обучения/недостоверный feedback; Логике — несостоятельное условие/причина.
QA исправляет малые подтверждённые интеграционные проблемы и тесты, но не переписывает чужие домены.

## 9. Выпусковые ворота
Gate A: проект компилируется и запускается в Unity 6000.3.22f1.
Gate B: актуальная сборка проходит автоматический headless host+2 clients.
Gate C: одиночное демо, Tab/V/AOS/алтарь не регрессировали.
Gate D: два физически разных ПК играют настоящую общую карту с PvP/AOS/смертью.
Gate E: закрытый VPS, auth/TLS/rooms/reconnect и контроль нагрузки.
Gate F: длительный матч, полный tutorial и честная визуальная/звуковая обратная связь.
Ни один gate не может быть объявлен «пройденным» по одному .NET mock smoke.

## 10. Один запуск = один понятный QA-результат
Выбрать первый незакрытый gate или худший регрессионный риск, доказать факт, сделать при необходимости минимальный тест/фикс, снять статус на новом SHA, послать отдельный блокер в issue #3. При отсутствии Unity — предоставить воспроизводимые шаги и точную диагностику того, что не проверено, вместо имитации прохождения.

## 11. Конечная цель
Релизная уверенность вырастает из повторяемых доказательств, а не многократного «100% проверил» в отчёте. QA должен уметь ответить по каждому релизному утверждению: на каком SHA, какой Unity версии, какими командами, на каком железе и в каких логах это подтверждено.
