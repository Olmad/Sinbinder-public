# Sinbinder — обязательный регламент пяти автоматических сессий
Версия: 1.0, 11.11.2026. Рабочая ветка: feature/server-prototype. Репозиторий: https://github.com/Olmad/Sinbinder-public.
Статус: обязательные правила работы и общий порядок передачи. Этот документ не означает, что планы остальных файлов уже выполнены.

## 1. Миссия и порядок ценностей
Мы поддерживаем уже играбельное одиночное демо Sinbinder и доводим сетевой режим, визуал, обучение, внутреннюю логику и качество интеграции до проверяемого состояния. Ценность определяется тем, насколько улучшена настоящая игра, а не количеством коммитов, строк кода или отчётов.

Приоритет решения: (1) безопасность данных и сохранность игрового проекта, (2) воспроизводимость и зелёные проверки, (3) сохранение существующей AOS и утверждённого управления, (4) полный игровой цикл и честная обратная связь, (5) удобство/визуальная полировка, (6) новые возможности. Временные блокеры или неработающая Unity-компиляция превосходят косметические задачи.

## 2. Неприкосновенные ограничения
- Ветку work-table НЕ открывать, НЕ читать, НЕ сравнивать, НЕ проверять и НЕ изменять, даже при ссылке на неё в документах или чужих отчётах. Никаких merge/cherry-pick из неё.
- Не изменять main, не сливать/закрывать черновой PR №1 без прямого указания пользователя. Работать только в feature/server-prototype, малыми проверяемыми коммитами.
- Существующее одиночное демо уже проходится. Не объявлять его «неиграбельным» на основе предположений. Никакой бездумной замены сцен, удаления контента, переименования Unity GUID или изменения игрового сценария.
- Tab = тактический вид / первое лицо. V = Командир / Воин только в первом лице и без смены камеры. Командир: ЛКМ выбор, ПКМ приказ. Воин: ЛКМ атака, ПКМ блок. Тактический режим сохраняется.
- AOS — настоящая многомодульная система характера/памяти/воли/страха/верности. Не заменять её упрощённым скриптовым соглашательством. Доставка приказа воинам != принятие приказа AOS.
- Для нейтрального воина возможность получить приказы от обоих Греховодов не означает исключительную принадлежность одному игроку. Разделять ownership, лояльность, временное выполнение приказа и командный статус.
- Сон/обучение: жёсткий язвительный Бог Смерти, без HUD-шкалы подавления воли; уроки требуют реальных игровых действий и правдивых объяснений. Лор и сюжет изменять только при явном подтверждении.
- Не передавать пароли/токены по plaintext TCP. Не открывать текущий прототип в публичный интернет, не делать платный VPS-деплой, не отправлять секреты в GitHub или логи.
- Не приписывать себе реальный Unity Play Mode, тест на двух машинах, зрительное или слуховое впечатление, если выполнены лишь проверка исходников, .NET Unity shim и TCP smoke.
- Не использовать защищённые чужие музыка/изображения/шрифты без прав и подтверждения лицензии.
- Не менять одновременно общие файлы других сессий. Никаких force push, переписывания чужих коммитов и самовольных массовых рефакторингов.

## 3. Роли, владельцы областей и минимальная периодичность
- Мультиплеер, :11 — Assets/Scripts/Multiplayer, сеть, server authority, LAN/VPS, lobby, synchronization, сетевой игровой цикл. Дорожная карта 10-MULTIPLAYER.md.
- Визуал, :23 — сцены/окружение, материалы, модели/генераторы, освещение, анимация/эффекты, визуальная читаемость. Дорожная карта 20-VISUAL.md.
- UX/обучение, :33 — обучение новичка, интерфейс и подсказки, объяснение AOS, удобство ввода и игровых переходов. Дорожная карта 30-UX-TUTORIAL.md.
- Логика, :41 — причинно-следственные контракты и игровые инварианты, последствия решений/смерти/спасения, неложные уроки и лор. Дорожная карта 40-LOGIC.md.
- QA/интеграция, :53 — CI, Unity сборка, регрессии, интеграционные/сетевые тесты, проверка совместимости патчей и релизные критерии. Дорожная карта 50-QA-INTEGRATION.md.

Времена — ориентиры запуска автоматизаций в Европе/Стокгольме. Они не гарантируют отсутствие перекрытий: один запуск может продолжаться, пока другой уже начал. Поэтому история GitHub — источник истины. Разделение обязанностей — право первичного изменения, не эксклюзивное владение файлами.

## 4. Источники истины и работа с неопределённостью
При расхождении сведений использовать по порядку: (1) последнее прямое решение пользователя; (2) конкретные события и логи проверенного Unity runtime; (3) актуальный HEAD и реальный исходный код; (4) прошедшие CI-тесты НА ЭТОМ SHA; (5) действующие планы/контракты; (6) исторические описания/идеи. Любое «реализовано», «проверено», «играется» требует точного доказательства и уровня проверки. Документы с прежними датами — история, не автоматически действующие инструкции.

Ссылки: PR https://github.com/Olmad/Sinbinder-public/pull/1; приоритеты мультиплеера https://github.com/Olmad/Sinbinder-public/issues/2; главный журнал координации https://github.com/Olmad/Sinbinder-public/issues/3; Assets/Scripts/docs/57-MULTIPLAYER-PRIORITIES-HANDOFF.md; Assets/Scripts/docs/65-TOTAL-TUTORIAL.md.

**Обязательная общая доска реальной готовности:** [Docs/AgentTeam/60-RELEASE-READINESS.md](60-RELEASE-READINESS.md). Каждая из пяти ролей перед новой работой сверяет свой gate G0–G7 с актуальным HEAD. QA вносит только доказанные результаты с ссылкой на CI/Unity/видео; без Unity ставить UNKNOWN/BLOCKED, а не PASS. Если CI красный, сначала чинить красный CI, не записывать предыдущий зелёный SHA в текущий.

## 5. Обязательная схема КАЖДОГО запуска
1. Проверить название ветки и текущий HEAD (SHA). Сначала не править.
2. Посмотреть последние коммиты, связанные изменения, запущенные и завершённые GitHub Actions на текущем SHA. Разделить ошибки сети, обучения, статических проверок и Unity.
3. Прочесть этот регламент, свою дорожную карту, issue #3 (описание и последние содержательные комментарии) и релевантную issue #2. Не копировать задачи без проверки актуального кода.
4. Определить один дефект или небольшое улучшение по своему приоритету. Письменно формулировать «игрок сейчас сталкивается с X; после патча будет Y».
5. Выполнить пре-проверку: какой текущий код и сцены участвуют, какие инварианты и соседние тесты должны сохраниться, кто редактирует те же файлы, какая тяжесть регрессии.
6. Если цель затрагивает общие файлы Gameplay/MapLoader/AOS/контроллеры, предварительно сообщить [В РАБОТЕ] в issue #3 с файлами и базовым SHA. Такой сигнал НЕ является надёжной блокировкой.
7. Реализовать один минимальный патч, не менять соседние системы без необходимости. Проверять sha файла прямо перед записью, при конфликте перечитать и согласовать либо отказаться от патча.
8. Добавить регрессионный тест для найденного дефекта или чёткий ручной сценарий при невозможности автоматизации. Тест должен ломаться на старом поведении и проходить на новом, если это возможно.
9. Проверить новое состояние по матрице уровней в разделе 7. Не заявлять успех на HEAD, если тест проходил только на предыдущем SHA.
10. Если красный CI — диагностировать источник. Если виноват текущий патч, исправить/откатить, не делать ещё пять фич. Если проблема в чужом файле, передать точный лог/файл/строку владельцу и обозначить блокировку.
11. Записать фактический результат в issue #3 только если есть существенная находка, патч или блокер: статус, SHA, изменённые файлы, проверки, кому адресовано. Обновить профильный backlog/PR, если изменился объём или статус возможности.
12. В конце коротко сообщить: что реально сделал, чего не делал, что нужно проверить в Unity, следующий конкретный шаг. Если нет подтверждённого изменения — не создавать фиктивный коммит.

## 5A. Почасовая работа, когда Unity недоступен

**Недоступность редактора НЕ является поводом отменять ежечасный запуск, повторять один и тот же блокер или называть работу завершённой.** Меняется только допустимый уровень доказательств: L0–L2 вместо L3–L7. Каждая сессия обязана найти полезный независимый следующий шаг, не требующий редактора, если он есть.

Порядок выбора:
1. Проверить текущие HEAD, CI, issue #3, новые коммиты соседей и существующие тестовые возможности. При красном CI расследование причины важнее новой функции.
2. Если для главной задачи нужен Unity, записать в журнал конкретный ручной сценарий и требуемые логи **один раз**, затем продолжить доступную параллельную работу по своему плану. Повторять тот же отчёт «Unity недоступен» без новых данных нельзя.
3. Выбирать реально проверяемую работу: source-level Unity API совместимость, GUID/serialized сцены, .NET unit и TCP integration, fuzz/negative tests, проверка логов и сборочных команд, UX/AOS математические инварианты и контрпримеры, анализ уже существующих материалов/моделей, локальные тесты без Editor.
4. Держать одну конкретную гипотезу и измеримый результат. Минимальная правка должна сохранять поведение и иметь регрессионный тест; рискованные визуальные/сценовые изменения без просмотра в Unity оставлять как подготовленный план, а не устанавливать вслепую.
5. **QA:** при отсутствии Unity искать build/CI scripts contract defects, error-code handling, неполную копию билда, несовместимость API, сцены/GUID, сетевые сценарии, достоверность сигналов PASS/FAIL. Упор на воспроизводимые проверки без Editor, а не на бесконечные сообщения о недоступности Unity.
6. **Мультиплеер:** реальный production C# bridge + .NET shim, протокол и безопасное восстановление, TCP server/client/visibility/attack security, regression tests. Не создавать очередную синтетическую игру вместо основной.
7. **Визуал:** инспекция scene YAML, материалов, шейдеров/путей, генераторов meshes, настройки UI и камер; исправлять только доказуемые дефекты без необходимости видеть кадр. Должна быть отдельная инструкция визуального осмотра для L4.
8. **UX:** проверять цепочки «действие → исход AOS → честная причина → подсказка», исходники текстов, условия уроков, edge cases и headless тесты. Новые утверждения о поведении реального новичка — только после плейтеста.
9. **Логика:** тесты инвариантов, контрпримеры и проверка причинно-следственных правил, включая death/rescue/осмысленность. Не переписывать лор ради зелёного теста.
10. При нехватке доступных безопасных задач дать содержательный подтверждённый аудиторский вывод и передать зависимость. **Не делать фиктивный коммит** и не обещать работу между запусками.

Приоритетный результат за час: исправленный воспроизводимый дефект с тестом > новый отрицательный тест на важный инвариант > конкретный подтверждённый блокер с планом воспроизведения > статический аудит с доказательствами. Количество коммитов НЕ целевая метрика.

## 5B. Требование закрытого цикла передачи между сессиями

Передача обнаруженного дефекта **не означает, что он исправлен**. У каждой существенной передачи должен быть владелец, точный пример воспроизведения, severity, SHA и проверяемый критерий завершения. Получатель в следующем запуске должен сверить актуальность проблемы (не повторять её автоматом), исправить или обозначить почему она не взята. Если проблема явно попадает в собственную область, по возможности исправить сразу вместо бесконечного перекладывания.

Для каждой важной передачи добавлять запись в issue #3 в формате [ПЕРЕДАЧА → Специализация], а при завершении [ГОТОВО → проверено уровнем Lx]. Избегать ложного успеха: никакая запись [ГОТОВО] без действительного теста соответствующего уровня не означает завершения целевой функциональности. QA должен выборочно перепроверять чужие интеграционные исправления, а не просто пересказывать отчёты.

## 6. Координация и конфликтующие правки
- Общий диспетчер: GitHub issue #3, не отдельные непроверяемые обещания в чатах. Сессии читают последние записи, прежде чем брать общую задачу.
- Формат комментария:
  [В РАБОТЕ/ГОТОВО/БЛОКЕР/ПЕРЕДАЧА]
  Сессия; проблема/факт; файлы и базовый SHA; что изменено; CI run URL + результат; тестовая среда; кому передано; следующий шаг.
- Для общих файлов особенно: MapLoader, SinbinderPlayer, Warrior, RivalLord, Damageable, AOS*, TugMatch, UI/контроллеры, *.unity, manifest.json, workflows. Любую общую правку по возможности согласовать; конфликт решать разбиением файлов, а не гонкой записи.
- Если обнаружена ошибка другой области: передать воспроизводимый сценарий и контрольные условия. QA может исправлять малые подтверждённые интеграционные дефекты при отсутствии конкурирующей правки, но не заменяет специализацию других.
- Коллективный приоритет: красный build/CI > разрушение соло > реальные network gameplay блокеры > реальные UX/AOS дефекты > косметика. Изложение «срочно» без воспроизведения не даёт приоритета.
- Никакой автоматической «приёмки» чужого патча. Каждая сессия отвечает за собственные тесты, QA проверяет поперечные риски, пользователь подтверждает реальный опыт игры.

## 7. Матрица доказательств и критерии качества
L0 — прочитан код / статическая проверка без исполнения. Нельзя говорить «работает».
L1 — чистая сборка .NET harness с Unity API shim, unit/contract test; фиксировать версию SDK, SHA, workflow.
L2 — TCP интеграционные тесты двух сокетов; подтверждают сетевые сообщения и правила сервера с моками, НЕ реальный Unity.
L3 — настоящая Unity 6000.3.22f1 Editor compile, импорт ресурсов/.meta и отсутствие missing scripts.
L4 — настоящий Unity Editor Play Mode и тест сцены, геймпад/мышь/камера, реальные NavMesh и rendering/audio.
L5 — собранный Unity Player + headless host + два клиента на одной машине, реальные логи, код завершения.
L6 — два физических компьютера LAN/VPN, геймплей и отказоустойчивость.
L7 — закрытый сервер/VPS с авторизацией/защищённым транспортом, стабильностью, логами и нагрузкой.
Ни один уровень не подразумевает следующий. Помечать «проверено» только на пройденном уровне. Параметры FPS/пинга/числа воинов не выдумывать.

Проверки регрессии при релевантных патчах: соло демо; Tab/V и камера; команда ЛКМ/ПКМ; AOS verdict и память; атака/блок; смерть/души/алтарь; две стороны; neutral allegiance; fog privacy; retry/timeout; старый тест капсул; сцены/Unity GUID; UI и аудио. Противоречивые результаты тестов сообщать явно.

## 8. Приоритет багов и стратегия исправления
S0: потеря файлов/данных, критичная уязвимость, уничтожение сценария/основной ветки — остановить новые работы; устранить риск.
S1: Unity не компилируется, матч не стартует/рушится, AOS заведомо лжёт, поломано управление/дублируются души, утечка секретов — прежде остальных фич.
S2: функциональная регрессия со способом обхода, неясное обучение, конкретный визуальный дефект, существенная нагрузка — исправлять планово и с тестом.
S3: эстетика, текст, микрополировка — после подтверждённой работоспособности.
Рейтинг: риск для игрока и регрессий > частота > воспроизводимость > сложность исправления. Не объявлять блокер без прямого свидетельства.

## 9. Определение завершённости (Definition of Done)
Задача Done ТОЛЬКО если: определена проблема/польза; изменён минимальный целевой код или ресурс; документирована проверка; код не противоречит решениям пользователя; CI на новом SHA оценён; нет неразрешённых регрессий в своей области; при нужном уровне выполнен Unity тест; отдельным абзацем указаны известные ограничения. Статус «Implementation complete, Unity unverified» разрешён. «Полностью готово», если нет L3–L6, запрещено.

Для крупных этапов — контрольная точка, а не бессрочная работа «до идеала»: конкретный измеримый сценарий, список файлов, тесты, границы, критерий остановки.

## 10. Нормальный отчёт и архив
Короткое описание сессии: [специализация][задача], HEAD до/после, изменённые файлы, 1–3 значимых следствия для игрока, тесты по уровням L0–L7, ссылки CI, риски, блокеры, следующий шаг. Один issue-комментарий на содержательную итерацию, без лент пустых статусов. Полные планы лежат в отдельных файлах ниже, текущий статус определяется GitHub HEAD и CI. Важные человеческие решения запрашивать, а не угадывать.

## 11. Реальный приоритет команды
1) Доказать настоящую Unity-сборку и 1 host + 2 clients, сохранить логи.
2) Общая настоящая карта и 2 реальных Греховода, а не только test capsules.
3) Полный AOS verdict + бой/смерть/души/алтарь и честная обратная связь.
4) Серверный fog of war, безопасность и защищённые комнаты/VPS.
5) Визуальная/UX полировка без деградации FPS, стабильность и релиз.

Не начинать крупную смежную систему, пока более ранняя критическая зависимость не подтверждена. Однако безопасные независимые мелкие улучшения можно вносить, не нарушая общий приоритет.
