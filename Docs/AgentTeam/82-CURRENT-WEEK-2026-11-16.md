Нельзя утверждать, что freeze технически обеспечен: почасовые автоматизации могут продолжать работу, пока их не остановили/не перенастроили. При тесте явно зафиксировать проверяемый SHA.

## 1. Единственный критерий успеха недели

Есть **один настоящий прогон Unity на зафиксированном SHA** (либо конкретный воспроизводимый blocker Unity Editor/Player), полноценный журнал `[AOS-5M]` и `[СОН QA]` по доступной части сна, **список проблем с доказательствами**, ранжированный по P0/P1/P2, и **одна** согласованная задача W02, обоснованная реальным эффектом для игрока.

Демо уже было проходимо автором раньше. Эта неделя не пытается заново «сделать игру играбельной». Она превращает личное знание автора в воспроизводимые данные, чтобы пять сессий не исправляли разные воображаемые проблемы.

**Более сильный успех:** 11/11 сценариев W01 имеют статусы PASS/FAIL/BLOCKED/NOT TESTED, но полный набор **не обязателен** для первой диагностики при ограниченном времени. Принципиально нельзя превращать NOT TESTED в PASS.

## 2. Максимум три задачи недели

- [ ] Зафиксировать SHA `feature/server-prototype` в момент запуска и версию Unity/ОС; не перепутать с позднейшими коммитами агентов.
- [ ] Импорт/compile с настоящими Unity DLL и старт из меню; записать Console с полным stack trace (особенно `Missing Script`, `error CS...`, `NullReferenceException`).

**Приёмка:** один конкретный Editor/Player лог/видео на SHA, чёткий результат G3/G4 либо blocker.

### Задача B — понять первые 5 минут и подлинность AOS (UX + Логика + автор)
- [ ] Фильтр Console `[AOS-5M]`; записать `new_game_clicked`, `first_command_detected`, `first_verdict`, `court_requested`, `court_coroutine_finished`, `second_verdict`/отсутствие с объяснением, `five_minute_mark` если сон не завершён к 5:00.
- [ ] Отдельно записать `[СОН QA]`, `[СУД]`; проверить **фактическое** действие против подписи «послушался», отклик J/Shift+J и видимость причины.
- [ ] Проверить один независимый приказ до/после изменения контекста, без подгонки AOS-исхода; если воин погиб — записать это как реальную ветвь, а не автоматический провал.
**Приёмка:** минутные отметки, один конкретный вывод «игрок увидел/не увидел автономную волю и почему», проблема с наибольшей стоимостью времени.

### Задача C — база проверки всей игры и выбор W02 (QA + остальные)
- [ ] По [11 сценариям](55-EVENING-UNITY-TEST-PLAN-2026-11-16.md) отметить PASS/FAIL/BLOCKED/NOT TESTED: кроме сна, бой/взаимное спасение, лагерь, сохранения (на копии), обе экспедиции/архив реплея, визуал, опционально 1 host+2 clients.
- [ ] Выделить TOP-3 настоящих дефекта; на каждый дать сцену/действие, expected/actual, строки Console, SHA, файл/видео, повторяемость и владельца.
- [ ] Назначить **ровно один** основной P0/P1 на W02; другие ошибки остаются в backlog, а не становятся ещё четырьмя независимыми направлениями.
**Приёмка:** краткий общий протокол, реальный следующий шаг и критерий исправления.

## 4. Как измерять, что именно стало лучше

**Текущий статус отдельных гейтов по материалам репозитория до вечернего прогона:**
- `G1/G2` профильные source/.NET/TCP CI: были success на **проверенном** SHA `ab4e7ec`, это историческое доказательство.
- `G3` Unity clean compile — **UNKNOWN в общей доказательной базе**, пока нет записи свежего Editor run.
- `G4` настоящее соло PlayMode, сохранения, AOS, сон — **UNKNOWN в общей доказательной базе** до протокола автора, хотя автор неоднократно играл демо ранее.
- `G5` общая реальная Unity LAN карта — **UNKNOWN/не завершена**, диагностические капсулы не считать реализацией.
- `G6/G7` первый слепой новичок/чистый другой ПК — **UNKNOWN**.

**Замер полезности недели:** число закрытых **подтверждённых** блокеров и сила доказательства; ни число коммитов, ни «40 минут работы», ни число отчётов не являются метрикой успеха. W01 может завершиться **без единого production-коммита**, если дала честный baseline и обоснованную W02.
