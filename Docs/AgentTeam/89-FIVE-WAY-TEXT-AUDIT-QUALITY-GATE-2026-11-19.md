Каждый имеет одну и ту же неизменную базу \`3b642a701a990ace58556b2afc2de04fd517b351\` и 582 перечисленных кандидата. Проверяются сохранность схемы/путей/исходных blob SHA, допустимые статусы, наличие доказательств. **Только новый или переписанный результат должен иметь доказательство QA2**; прежние неполные свидетельства учитываются с предупреждением, а не молча превращаются в PASS. ## 2. Контракт одной записи аудита

Пример в единственном поле \`evidence\` (строка TSV без вкладок и переносов):

\`\`\`text
QA2: source=Assets/Scripts/Gameplay/Whisper.cs; blob=PUT_REAL_40_CHAR_SHA_HERE; lines=50-61; context=Words(SinType.Lust) without NPC presence gate; negative=no woman in demo; verified=0; total=1; RU_EN=UNKNOWN; outcome=UNKNOWN
\`\`\`

**Указывать реальные SHA и строки**, а не копировать заглушку. В текущем TSV остаются десять существующих колонок: \`path\`, \`blob_sha\`, \`bytes\`, \`audit_class\`, \`found_text_candidates\`, \`checked_text_candidates\`, \`failed_text_candidates\`, \`unknown_text_candidates\`, \`status\`, \`evidence\`.

Правила для чисел:
- \`found\`: реально обнаруженные player-facing кандидаты в пределах данного источника (если известна только часть, записать границу и недостающее в evidence; не присваивать PASS).
- \`checked\`: кандидаты, для которых прочитана фраза и проверены контекст/путь отображения на указанном уровне. Просто grep не считается семантической проверкой.
- \`failed\`: проверенные строки с подтверждённым контрпримером; \`0 <= failed <= checked <= found\`.
- \`unknown\`: строки с незакрытым контекстом; \`0 <= unknown <= found\`. \`unknown\` и \`checked\` могут пересекаться только если ясно указаны разные уровни проверки; в QA2 явно различать «прочитано», «верифицировано».
- \`verified/total\`: количество смысловых выводов, которые подтверждены на указанном уровне. Для PASS обязаны быть равны, \`total = found = checked\`, \`unknown = failed = 0\`, RU/EN и контрпример подтверждены.
- \`EXCLUDED_TECH\`: только после чтения источника и доказательства, что **ни одна** строка из него не видна игроку. Все четыре счётчика 0. Связанные визуальные/генерируемые источники отмечать UNKNOWN отдельно.
- \`FAIL\`/ \`PARTIAL_FAIL\`: хранить воспроизводимый отрицательный тест с входами и фактическим результатом; это не значит, что каждый runtime путь достижим без дополнительной проверки.

У каждого отчёта явный статус \`SOURCE_STATIC\`, \`SOURCE+TEST\` или \`UNITY_VERIFIED\`; не писать UNITY_VERIFIED без действительного запуска. Для динамических/бинарных текстов статус UNKNOWN до проверки.

**Важно:** ещё встречаются старые записи с \`checked > found\` и \`unknown > found\`; они помечаются \`LEGACY warning\`. При следующей смысловой проверке именно этих строк их необходимо привести к новой схеме, объяснив изменение счётчиков; нельзя подгонять числа ради зелёного CI.

## 3. Приоритет обхода без отказа от независимости

Каждая из пяти сессий проверяет **все** источники. Приоритет внутри каждого прохода:
1. P0: \`Whisper\`, \`BattleNarrator\`, причинность Суда и AOS, ложные имена/пол, обещания, награды и последствия;
2. P1: \`DialogueDatabase\`, \`EncounterLines\`, диалоги лагеря/деревень, экспедиции, сон/Tab/V, HUD/подсказки, EN;
3. P2: все остальные player-facing и затем технические исключения; binary/visual/dynamic источники явно помечать.

Этот порядок не означает, что технические файлы можно навечно пропустить. Выбор новой задачи: сначала продолжение текущего файла/пакета, затем следующий приоритетный источник с \`UNINSPECTED/UNKNOWN\`. В каждом запуске сохраняется checkpoint и законченная проверка хотя бы ограниченного набора строк; если законченного набора нет, честный \`INCOMPLETE\` и никаких выдуманных коммитов.

**Приёмочный охват**: не «хотя бы один аудитор проверил», а для каждого из пяти отдельно 582/582 с техническими обоснованиями исключений, все игровые реплики контекстно оценены, все FAIL разрешены либо явно приняты автором как осознанный текст, UNKNOWN вынесены в финальный риск-реестр.

## 4. Безопасность параллельных коммитов

1. Каждый аудитор владеет исключительно своим \`88-INDEPENDENT-AUDITOR-N-PROGRESS.tsv\`. Никто не правит чужой TSV.
2. Перед записью повторно прочитать текущий blob SHA своего TSV и актуальный HEAD \`feature/server-prototype\`. Применить минимальную замену **своих** строк через \`update_file\` с optimistic SHA.
3. На конфликт 409/422: извлечь актуальную версию своего TSV; сопоставить статус/содержание строки; **rebase только своё изменение**. Не делать force push, overwrite чужого содержимого, merge чужих веток или переписывать базовые файлы инвентаря.
4. QA-сводка вычисляется в GitHub Actions как артефакт, а **не** переписывается пяти агентами в одном Markdown файле. Это исключает одну из самых частых гонок.
5. Если CI не проходит, изучить фактический лог и исправить TSV доказательства; не отключать workflow и не маскировать статус.

## 5. Передача подтверждённых FAIL в безопасные исправления

- Аудиторы №1–3 находят контрпримеры и регистрируют evidence в личных TSV.
- **№4 единственный владелец малых production-патчей.** На каждый: точные входы, отрицательный пример в старом коде, минимальная правка, положительный и отрицательный тест, локализация RU/EN, проверка сохранений и AOS/Tab/V. Один пакет за раз. Не переписывать авторские реплики ради красивого стиля. Не менять голосовую механику без решения автора.
- **№5 независимо перепроверяет патч №4** на точном commit SHA, особенно неверные обещания, несуществующих персонажей, случайные причинные выводы. Помечает QA_ACCEPTED/QA_REJECTED с причинностью, тестами и неопределённостями. Отказ не стирает прежнюю находку.
- Известный предмет для исправления: \`Assets/Scripts/AOS Engine/BattleNarrator.cs\`, \`Build(null)\` заявляет о послушании при отсутствии данных; \`entries.Count > 4\` ошибочно делает вывод о переговорах по одному количеству записей. Исправлять именно ложные выводы, а не смысл движка боёв.
- \`Whisper\` «Она смотрит» остаётся отдельным подтверждённым контекстным дефектом и не должен быть закрыт без исправления условий/текста и RU/EN.
