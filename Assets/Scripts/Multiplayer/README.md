# Sinbinder: встроенный LAN-тест (ветка feature/server-prototype)

## Что реализовано

Это **отдельный сетевой песочничный режим**, а не готовый сетевой
«Перетягивание каната» или кооператив сюжетного демо.

- Unity запускает сервер **внутри самого игрового процесса**. Не требуется
  .NET 8, установка отдельного Netcode-пакета, создание сцены вручную или
  настройка NetworkManager.
- Два участника подключаются по TCP; у каждого свой идентификатор,
  кнопка готовности и собственный персонаж на тестовой арене.
- Для `-lan-connect ... -lan-auto-ready` клиент сам повторяет
  подключение до 30 раз с интервалом 2 секунды: второе окно может
  загрузиться раньше хоста. При ручном подключении предусмотрена
  кнопка **«Повторить подключение»**.
- Только сервер назначает тик/порядок приказов, принимает Move/Hold,
  проверяет владельца, координаты и ограничения частоты команд,
  рассчитывает перемещение и рассылает позиции обоим игрокам.
- Ограничен размер сообщения, есть таймаут исходящего пакета,
  отключение прекращает матч. Клиенты отправляют heartbeat каждые
  2 секунды, клиент сообщает о молчании сервера через 12 секунд,
  Unity-хост освобождает место молчащего клиента через 20 секунд.
  Внешний .NET сервер также понимает heartbeat и ограничивает
  время ожидания очередного входящего пакета 20 секундами.
  Задачи сети не обращаются к Unity API вне главного потока.
- Сцена одиночной игры **временно скрывается**, пока активен тест.
  При выходе её корневые объекты возвращаются. Файлы сцены, управление
  Tab/V и сценарный код не переписываются.
  Постоянный `SelectionManager` на это время выключается, а после выхода
  восстанавливается, чтобы он не перехватывал мышь в тестовой арене.
  В тестовую арену добавляется собственное освещение.
- Код не использует Unity Netcode. Это минимальная самостоятельная
  TCP-вертикаль; для релизной игры нужен дальнейший архитектурный выбор.

## Первый запуск в Unity

1. Открой проект **Unity 6000.3.22f1** на ветке `feature/server-prototype`.
2. В редакторе нажми **Play**.
3. В правом верхнем углу нажми **LAN тест** → **Создать LAN**.
4. Запусти второй экземпляр собранной игры, **LAN тест** →
   **Подключиться**, адрес `127.0.0.1` (если на том же ПК) или LAN IP
   компьютера-хоста. Порт `7777`.
5. Оба нажимают **Готов**. Правой кнопкой по полю перемещают *свою*
   капсулу. Обе машины видят положение обеих капсул.
6. Нажми **Выйти из теста**, чтобы вернуться в одиночную игру.

Для двух окон одной сборки после сборки через `Собрать игру.cmd`:
**дважды щёлкни `Test-LAN.cmd` в корне репозитория**. Скрипт
откроет оба окна с автоматическим подключением и готовностью.

Варианты запуска:

```text
Sinbinder.exe -lan-host -lan-auto-ready -port 7777
Sinbinder.exe -lan-connect 192.168.1.20 -lan-auto-ready -port 7777
Sinbinder.exe -batchmode -nographics -server -port 7777
```

Последняя команда запускает **выделенный тестовый Unity-сервер**
без окна: два клиента отдельно подключаются по IP.

Для проверки без UI:

```sh
python Tools/server/unity_smoke_test.py --host 127.0.0.1 --port 7777
```

Этот скрипт подключает два настоящих сокета, проверяет приветствие,
готовность, запрет чужих приказов, серверное расписание, изменение позиции
и остановку при отключении. Нужен запущенный Unity-сервер. Он не
заменяет запуск Unity и не утверждает, что тест уже пройден.

## Карта механик и визуальный алтарь

Кроме синтетической сетевой арены в ветке есть **отдельная настоящая
игровая сцена** `Assets/Scenes/Tug/Multiplayer_Test.unity`. Она использует
тот же набор менеджеров, UI и `MapLoader`, что исходная сцена `Field`.
Её можно открыть непосредственно в Unity, запустить через кнопку
**«Карта механик (локально)»** в меню LAN или выполнить
`Test-Mechanics.cmd` после сборки.

Карта размером 240 × 240 м включает два склепа с троном, дверью и
функциональным алтарём связывания; пять нейтральных поселений/полей/
лесов с жителями, противника `AiMedium`, два входа охотников, четыре
точки событий, палатки, костёр и интерактивные предметы. В ней можно
проверять существующие **AOS, приказы, навигацию, бой, рекрутирование,
смерть/возвращение Греховода, трофеи, события, охотников и Великую охоту**,
если соответствующие механики доступны в текущей версии оригинального
`MapLoader`. Создание карты из файлов оригинальной системы не заменяется
новой логикой.

**Существенное ограничение:** карта механик пока **локальная** и запускает
второго Греховода как ИИ. TCP/LAN-прототип из раздела выше *не*
синхронизирует этот игровой мир, AOS или боевую систему. На текущий момент
это два разных теста: корректности сетевой доставки и корректности
реальных игровых механик. Иначе говоря, это НЕ готовая сетевая битва
«со всеми механиками».

Визуальная отделка `AltarVisualEnhancer` запускается автоматически при
загрузке сцен: у функционирующего `BindingDevice` и сюжетного
`Altar.fbx` появляются тёмные каменные ступени, бронзовые обручи,
светящиеся руны, кристаллы душ и холодное локальное освещение.
**Ни один существующий рычаг, коллайдер устройства или сокет не
изменяется**. Новые декоративные примитивы создаются с отключёнными
коллайдерами, чтобы не мешать перемещению и взаимодействию.

## Безопасность и ограничения

- Сервер слушает **все локальные IPv4-интерфейсы** (`0.0.0.0:7777`);
  используйте только локальную сеть / доверенную VPN.
- TCP, без авторизации, шифрования, NAT traversal, защиты от DDoS и
  сетевого восстановления после разрыва. **Не открывать порт в интернет**.
- Между двумя компьютерами может потребоваться разрешить TCP 7777
  в брандмауэре Windows; это настройка ОС, не кода.
- Оба клиента должны иметь совместимую сборку. Встроенный Unity
  LAN-хост и экспериментальный внешний .NET сервер используют один
  тестовый JSON-протокол и **оба** симулируют перемещение двух капсул.
  Внешний сервер необязателен, а реального игрового мира ни один из них
  пока не симулирует.
- **Существующие Warrior, AOS, NavMesh, MapLoader, FogOfWar и игровые
  сохранения пока не синхронизируются.** Тестовая арена использует
  простую капсулу, а не боевой префаб.
- GitHub Actions проверяет сборку внешнего сервера на .NET 8,
  компиляцию всех пяти новых Unity LAN-скриптов на тестовых заглушках
  UnityEngine и сетевые тесты: два игрока, движение, отключение,
  переподключение, перегрузка входящей очереди, отказ чужому игроку
  в приказе, превышение количества участников, ограничение частоты,
  heartbeat, таймауты молчания, 12 циклов Stop/Start на одном порту
  и проверку восстановления тестовой арены.
  ПКМ по кнопкам панели LAN не отправляет игровой приказ.
- **Настоящая сборка и Play Mode в Unity 6000.3.22f1 всё ещё не
  выполнялись.** Тестовый компилятор API не заменяет Unity Editor.

## Новый фундамент настоящих игровых приказов

В дополнение к старой сетевой арене в этой ветке добавлен **отдельный
авторитетный слой для реальных воинов**:

- `MatchAuthority.cs`: назначает серверные ID сущностей, связывает
  соединение с именем Греховода и стороной, проверяет команду, номер
  партии, повторную отправку, координаты, владельца и видимость цели.
- `NetworkActorIdentity.cs`: прикрепляет ID и ID матча непосредственно
  к Unity GameObject зарегистрированного воина; не позволяет сменить
  активную сетевую идентичность произвольно.
- `ServerWarriorOrderBridge.cs`: принимает **уже проверенный сервером**
  приказ, ставит в ограниченную очередь (не более 512 запросов) и
  передаёт его реальному `Warrior.IssueCommand` либо `IssuePatrol`
  **только на назначенном серверном тике** через `ProcessDue`.
  Устаревший приказ погибшему воину, исчезнувшей цели или
  отключившемуся Греховоду не исполняется.
  Атакующая цель берётся из состояния сервера, а не из клиентских
  координат; слышимость и видимость определяются сервером.
- `Warrior.IssuePatrol` получил необязательный аргумент `lord`,
  чтобы патруль нейтрального воина не превращался в приказ первого
  локального игрока. Старые вызовы и одиночная игра сохранены.

**Ключевое правило:** `NeutralWarrior` не принадлежит эксклюзивно
первому, кто отдал приказ. Оба Греховода могут предлагать ему свои
действия, а AOS уже оценивает их согласно его характеру и верности.
`Lord` и явно принадлежащий стороне `AffiliatedWarrior` принимают
команды только от авторизованного подключения своей стороны.

`Tools/server/UnityLanHarness/AuthorityChecks.cs` проверяет
защиту от подмены Греховода, устаревших/повторных команд, запрет
невидимой цели, возможность двух независимых приказов нейтральному
воину, метки идентичности и вызов настоящего API Warrior
(через C#-заглушки игровой среды).

### Настоящая карта: реестр воинов и проверка игрового LAN-транспорта

`ServerWorldProbe.cs` устанавливается **только** в `Multiplayer_Test`
при аргументе `-mp-world-probe` (локальная диагностика) или
`-mp-world-host` (отдельный TCP-хост игрового мира).
Он сканирует настоящие `Warrior`, назначает им ID, отличает
`SinbinderPlayer`, `RivalLord`, нейтральных и стороновых бойцов,
удаляет мёртвых и продвигает очередь AOS на серверном тике 20 Гц.

**Три теста, три разных назначения:**

- `Test-LAN.cmd`: старая независимая арена из двух капсул, базовое
  соединение, лобби, Move/Hold, снимки координат капсул.
- `Test-World-Probe.cmd`: реальная локальная карта,
  регистрация/удаление Warrior без сетевых клиентов.
- **`Test-World-LAN.cmd`**: запускает настоящий Unity-хост карты
  (`-mp-test-map -mp-world-host -port 7786`) и два LAN-клиента.
  Клиенты видят **только прежнюю арену капсул**, а не эту карту.
  После готовности обоих игроков каждый может нажать **F8**:
  запрос `gameOrder` с ID **своего** Греховода идёт по TCP в хост,
  сервер проверяет отправителя, планирует `Move` и возвращает
  `gameAccepted` и затем `gameResolved`. Хост записывает данные
  в `Build/Sinbinder/WorldHost.log`. Клавиша ПКМ в старой арене
  продолжает двигать только синтетическую капсулу.

В дополнение к старому `order` реализован самостоятельный протокол:
`gameMatch` выдаёт идентификатор партии, разрешённый ID собственного
Греховода и последний подтверждённый номер команды;
`gameOrder` содержит `MatchId`, `CommandId`, `ActorId`,
тип, цель и координаты. Сервер берёт подлинный ID отправителя
**только из TCP-соединения**, не из пакета.
`gameAccepted/gameRejected` возвращают результат проверки,
`gameResolved` сигнализирует о доставке намерения к `Warrior`
на нужном серверном тике. **Это НЕ означает, что AOS согласился
исполнить приказ:** его голосование идёт после доставки.

Сообщения о результате исполнения отправляются только автору
приказа. Чужие ID и скрытые позиции не рассылаются. Если нет
авторитетного фильтра видимости, приказы `Attack` отклоняются.

**Новый частичный снимок реального игрового мира.**
`ServerWorldProbe.GetPrivateWorldActors` фильтрует живых воинов
*отдельно для каждого соединения*; без серверной политики
`CanObserveActorOnServer` возвращает **только своего Греховода и
принадлежащих своей стороне воинов**. Нейтральные и противники не
отправляются, даже если одиночный `FogOfWar` показывает их.
Когда будет реализован авторитетный туман войны по сторонам,
`CanObserveActorOnServer` должен проверять его на сервере, а не
пользоваться локальной клиентской маской.

Хост отправляет ограниченные снимки (не больше 24 сущностей на игрока)
через `worldBegin/worldActor/worldEnd` приблизительно раз в 0,25 секунды.
Клиент обновляет список только после **полного кадра**. Когда сущность
погибла или перестала быть видимой, она удаляется из следующего
корректно полученного снимка. Сейчас пересылаются **только ID, роль и
координаты**: здоровье, AOS-память, бой, инвентарь и полноценная карта
в этой структуре ещё отсутствуют.

В `Test-World-LAN.cmd` приватные игровые координаты показываются на
упрощённом диагностическом поле 1:12 в виде небольших неинтерактивных
маркеров. В меню отображаются число видимых серверных воинов, тик
игрового мира и координаты собственного Греховода. Это **не 3D-карта
игрового мира**, а проверка реально передаваемых данных; два больших
капсульных персонажа остаются независимым исходным LAN-тестом.

`WorldSnapshotChecks.cs` проверяет поток по двум настоящим TCP-сокетам:
каждый видит только свои ID, координаты обновляются, разрешённый
нейтральный виден только одной стороне, скрытие/смерть удаляют его
из снимка, неполный кадр не заменяет достоверные данные.

**Ограничения:** это первая интеграция реального игрового API с
LAN-транспортом. *Удалённым клиентам пока не передаётся полноценная
карта, AOS, NavMesh, бой или туман войны*. `RivalLord` остаётся
ИИ, а не управляемым вторым человеком, и его собственные решения
пока могут конфликтовать с сетевыми. Нет безопасной публикации
видимых нейтральных актёров и команды их выбора в игровом UI.
Никаких обещаний настоящего сетевого матча на этом этапе.
Использовать только доверенную LAN/VPN.

Автотест `Tools/server/UnityLanHarness/GameOrderWireChecks.cs`
реально открывает два TCP-клиента, проверяет запрет чужого Lord,
приказы одному нейтральному `Warrior` от двух сторон,
очередь серверного тика, закрытые персональные ответы,
отмену после разрыва и переподключение *новым* клиентом без
повторного номера команды.

## Продолжение до настоящего Sinbinder Multiplayer

1. Выделить серверное владение каждой стороной/Греховодом и юнитами.
2. На сервере запускать имеющиеся решения `BehaviourResolver`, AOS,
   боевую систему, NavMesh и события; на клиентах только отображать
   разрешённое состояние. Не пытаться детерминированно просчитывать
   Unity NavMesh на независимых машинах.
3. Сетевые ID выдаёт сервер при спавне. Не использовать
   `Warrior.Id` (локальный Guid.NewGuid).
4. Настоящие приказы из `SelectionManager` превращать в намерения,
   проверять голос, владение и допустимость действия на сервере.
5. Отдельно синхронизировать исходы голосования AOS с объяснениями,
   здоровье, смерть, постройки, ресурсы, туман войны, журнал своего
   Греховода. Не пересылать скрытые данные чужой стороны.
6. Интеграционный тест с двумя Unity-клиентами и выделенным сервером,
   с отключением и переподключением, до переноса в реальную карту.

Ни один `.cs.later` файл не активирован, основное демо не менялось.
