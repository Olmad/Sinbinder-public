# 02 — Architecture of the Soul

## Принцип

> Не программируй поведение. Программируй личность.

Дизайнер не пишет «если союзник ранен — спасай». Дизайнер задаёт характер,
а поведение появляется само. Если поведение приходится прописывать вручную —
архитектура нарушена.

Пять правил, которые нельзя нарушать:

1. **Личность — причина, поведение — следствие.**
2. **Отношения не хранятся, а вычисляются из памяти.** Забылось событие —
   растворилось и отношение.
3. **Любое решение объяснимо.** Если разработчик не может ответить «почему
   он так поступил» — система сломана.
4. **Модули не знают друг о друге.** Влияние проходит только через голосование.
5. **Случайность — не характер.** Рандом допустим только чтобы разрешить
   ничью, никогда — как причина поступка.

## Как это работает на самом деле

Конвейер в `BehaviourResolver.Decide()` — **РАБОТАЕТ**:

```
Warrior + мир
      │
      ▼
CombatDecisionContext.Create()      неизменяемый снимок ситуации
      │
      ▼
8 модулей голосуют независимо        каждый оценивает каждое действие
      │
      ▼
вес эмоции × оценка модуля           EmotionSystem как линза, не как правка личности
      │
      ▼
складываем, сортируем
      │
      ├── разрыв < 10 → Idle         «колеблется»
      └── иначе → победитель
      │
      ▼
AOSWarriorWrapper.Execute()
      │
      ▼
MemoryProcessor записывает исход      память кормит следующее решение
```

Подключённые модули (8): Greed, Wrath, Virtue, Fear, Loyalty, Morality,
Memory, Sloth. Написан, но **не зарегистрирован**: Patience.

## Подчинение — исход голосования, не обход его

Это ядро замысла, зафиксированное автором.

Приказ игрока не исполняется напрямую. Он становится **фактом контекста**
(`DecisionContext.HasCommand` + `CommandType`) и добавляет очки действию
`ActionType.ObeyCommand`. Сколько очков — решает `LoyaltyModule`:

```csharp
if (context.HasCommand && action == ActionType.ObeyCommand)
    score += soul.Loyalty * _config.LoyaltyObeySinMultiplier;
```

Приказ побеждает, когда верность перевешивает всё остальное. Жадность может
его перебить (`GreedObeyUnpaidPenalty = -40` при трёх невыплатах), страх
может увести в бегство, память о предательстве может обнулить верность.

**Это не баг и не поблажка ИИ. Это и есть игра.**

Статус: **НАПИСАНО, НЕ ПОДКЛЮЧЕНО** — цепочка разорвана в трёх местах,
подробности в `03-STATUS.md`.

## Память

Три уровня, все **РАБОТАЮТ**:

- **Рабочая** — свежие события, высокая важность
- **Долговременная** — то, что пережило затухание
- **Эмоциональный след** — деталей нет, чувство осталось

Формула силы воспоминания (`MemoryRecord.GetCurrentStrength`):

```
Strength = Importance × |вес эмоции| × Recency × знак веса
Recency  = 1 / (1 + Age × DecayRate)
```

Затухание гиперболическое, не линейное: свежая обида забывается быстро,
старая — почти никогда. Это правильно и соответствует замыслу.

Отношения (`RelationshipSystem`) вычисляются как сумма сил общих
воспоминаний. Отдельного числа «отношение = +37» не существует, и оно
не должно появиться.

## Эмоции

`EmotionSystem` не меняет личность — она меняет **вес** модулей на время:

| Эмоция | Что усиливает | Что глушит |
|---|---|---|
| Страх | Fear ×1.5 | Wrath ×0.5 |
| Гнев | Wrath ×1.5 | Virtue ×0.5 |
| Радость | Loyalty ×1.3 | — |
| Печаль | Fear ×1.3 | всё остальное ×0.9 |

Затухание: −0.1 за такт. Испуганный воин временно труслив, но не становится
трусом навсегда. Личность неприкосновенна — линза временная.

## Две структурные поломки

Обе найдены при аудите, обе — Уровень 0 в `04-ROADMAP.md`.

### Личность одномерна

`SoulData` хранит **один** грех и **одну** интенсивность. Но все модули
читают одно и то же поле:

```csharp
// GreedModule, WrathModule, SlothModule, VirtueModule, PatienceModule
float sin = soul.SinIntensity;   // одно число на всех
```

Значит воин с `SinIntensity = 80` одновременно предельно жаден, предельно
гневлив и предельно уныл. Все воины — один и тот же коктейль, отличаются
только силой. Это ровно тот провал, которого мы боимся под номером 2.

Диздок обещает семь спектров «грех ↔ добродетель». Кода под это нет.

**Лечение:** `SoulData` получает набор из семи шкал (−100…+100), каждый
модуль читает свою. `Sin` и `SinIntensity` становятся производными —
«доминирующий грех» вычисляется как максимум по модулю.

Побочный выигрыш: добродетели перестают быть отдельной сущностью. Щедрость
— это Жадность со знаком минус. Семь шкал вместо четырнадцати понятий.

### Действий 62, голосуют 6

```csharp
Dictionary<ActionType, float> scores = new()
{
    { Attack, 0 }, { SaveAlly, 0 }, { Loot, 0 },
    { Flee, 0 }, { Idle, 0 }, { ObeyCommand, 0 }
};
```

В `ActionType` 62 значения. Все навыки — Berserk, GoldRush, Charm, Devour,
ShieldOfFaith и прочие — в голосование не попадают никогда. Файлы
`WrathSkills`, `LustSkills`, `SlothSkills` написаны, но AOS физически
не может выбрать то, что в них лежит.

**Лечение:** набор кандидатов собирается из того, что воин *умеет*
(класс + оболочка + перки + доступность), а не жёстко из шести.

## Прозрачность: лестница из четырёх ступеней

Правило: **игрок никогда не видит цифр.** Он видит поступки и объяснения
на человеческом языке. Цифры — инструмент разработчика.

| Ступень | Что показываем | Когда |
|---|---|---|
| 1. Значок | ⚔ 🛡 💰 🏃 ❓ 🤝 над головой | всегда, в момент решения |
| 2. Подсказка | одна фраза при наведении: «Золото ближе, чем приказ» | по наведению |
| 3. Журнал боя | связный рассказ о том, кто что решил и почему | после боя |
| 4. Трассировка | голоса модулей, веса, разрыв | только для разработчика |

Ступени 1 и 4 существуют (`DecisionIconUI`, `Debug.Log` в резолвере).
Ступени 2 и 3 — **СПРОЕКТИРОВАНО**. Именно они закрывают провал №1
(нечитаемость), и именно их отсутствие обычно убивает такие игры.

Пример правильной ступени 3 — без единой цифры:

> **Марга Копатель** не пошёл на мост.
> Ему не платили третью вылазку подряд, а в развалинах блестело золото.
> Приказ он слышал. Просто золото было громче.

Пример неправильной:

> Марга: Greed 47.5, Loyalty 12.0, победа Loot с разрывом 35.5

## Детерминизм

Одинаковые личность + память + контекст + зерно случайности = одинаковое
решение. Это обязательно: без воспроизводимости невозможно ни отладить
поведение, ни объяснить его игроку.

Сейчас соблюдается. `Time.time` в затухании памяти — единственное место,
где значение зависит от момента; при записи реплея его надо фиксировать.

## Производительность

Volume II заявляет ≤0.5 мс на воина и **ноль аллокаций**. Фактически
`Decide()` на каждый вызов создаёт: словарь очков, объект `Soul`,
по одному `List` на каждый из 8 модулей (`scores.Keys.ToList()`),
две сортировки LINQ и ещё один `ToList()`. Около 13 аллокаций на решение.

При 20 воинах и нескольких решениях в секунду это заметная нагрузка на
сборщик мусора. Не срочно — но заявленной цели код не соответствует,
и в диздоке это должно быть написано честно.

Лечение простое и откладываемое: переиспользуемый массив очков вместо
словаря, `Soul` как поле-буфер, ручной поиск максимума вместо LINQ.

## Чего AOS не делает

Не ищет путь. Не анимирует. Не генерирует текст диалогов. Не моделирует
сознание. Не обучается.

AOS отвечает ровно на один вопрос: **что этот персонаж хочет сделать
прямо сейчас.** Исполнение — чужая забота.
